# Demonstration

Three demonstrations. The first is the one worth watching, because it shows the same
hardware before and after a contract governed it.

---

## 1. The same axis, before and after the contract

Two recordings of the same rig, four months apart.

| | June 8 2026 | September 30 2026 |
| --- | --- | --- |
| Recording | `evidence/demo_2026-06-08_manual_unbounded.mov` | `evidence/demo_2026-09-30_generated_tilt_bounded.mov` |
| Firmware | hand-written | generated by HAMR from the SysML v2 model |
| Commanding | one command per axis, issued by hand | `/scan/start`, plan executed by the generated `ScanController` |
| Tilt axis | turns freely; no limit | stops at ±45° and refuses to go further |
| Length | 27 s | 24 s |

Same motors, same drivers, same wiring. What changed is that the tilt axis is now governed
by [`SI-MCU-9`](../sysmlv2/SeedImaging.sysml#L277), a GUMBO guarantee in the model.

In the September recording the axis reaches 45° and the next command produces no motion.
That refusal is the demonstration. The command is accepted, acknowledged with the unchanged
position, and the motor does not turn.

### What the pairing shows

| Layer | Artefact |
| --- | --- |
| Physical finding | past ±45° the tilt bracket occludes the camera for seeds under 3 mm |
| Model constant | `TILT_LIMIT_STEPS = 25` |
| GUMBO predicate | [`isSafeTiltMove`](../sysmlv2/SeedImaging.sysml#L91) |
| Guarantee | [`SI-MCU-9`](../sysmlv2/SeedImaging.sysml#L277) |
| Proof | Logika discharges it over the generated Slang |
| Test | `compute_GUMBOX_manual_SI_MCU_9: X level, +26 is refused` |
| Generated C | the micro-ROS node on the MCU |
| Hardware | the motor does not turn |

The June recording is the control. Without the contract, nothing in that chain existed and
the axis had no limit.

**Refused rather than clamped.** The position is still published, so the host learns the
true state rather than a value it did not ask for. A clamp would silently move the axis
somewhere that was not requested.

## 2. Verification has teeth

`bin/seeded_bug_demo.sh esp32 | jetson | model`

Three deliberate faults, each caught by a different mechanism. Roughly two minutes each, no
hardware required, and it runs from the repository on any machine with Sireum installed.

The `model` case is the one to show if only one is shown: neither component is faulty in
isolation, both pass their own tests, and the fault is caught at the connection before code
generation. See [Testing.md](Testing.md#fault-injection).

Captured output in `evidence/`: `bug_esp32.txt`, `bug_jetson.txt`, `bug_model.txt`.

## 3. The model drives the hardware

1. `bin/verify.sh` — seven checks pass
2. `bin/hamr.sh` then `diff` — regeneration is byte-identical to what is deployed
3. Change one value in `SeedImaging.sysml`, regenerate, reflash, re-run — the hardware moves
   differently

Step 3 takes roughly 20 minutes end to end, since it requires reflashing the MCU and
rebuilding on the Jetson. The June/September pairing above is the same argument already
made, over a longer interval and a larger change.

## Reproducing the tilt demonstration

**Setup.** Both nodes up, 12 V connected, tilt levelled by hand and the ESP32 reset so the
axes are at the home position [`SI-MCU-1`](../sysmlv2/SeedImaging.sysml#L230) assumes.

**Three commands.** Values are relative steps.

```
ros2 topic pub --once /stepper/x/cmd std_msgs/msg/Int32 "{data: 25}"
```

Tilt rises to +45°. [`SI-MCU-8`](../sysmlv2/SeedImaging.sysml#L273): a safe bounded command
moves exactly the commanded steps.

```
ros2 topic pub --once /stepper/x/cmd std_msgs/msg/Int32 "{data: -50}"
```

Full 90° sweep to −45°, in one move. The largest legal move on this axis.

```
ros2 topic pub --once /stepper/x/cmd std_msgs/msg/Int32 "{data: -1}"
```

Nothing moves. The axis holds at −45° and `/stepper/x/pos` continues to report −25 steps.

## If demonstrating live

Three failure modes have each cost a session, and all three are procedural.

**Only one micro-ROS agent.** Two agents both claim `/dev/ttyACM0` and fight over it. The
link appears and disappears about once a second, which looks like a hardware fault and is
not. Run `sudo docker ps` before starting and stop anything listed.

**Connect the ESP32 directly to the Jetson**, not through a hub. If `/dev/ttyACM0` is
missing and `dmesg` shows repeated `error -110`, the USB controller is wedged and needs a
reboot rather than more replugging.

**12 V must be connected.** With it unplugged the ESP32 still runs on USB and accepts every
command, publishing positions and acknowledging normally while nothing moves.

Pre-flight: `sudo docker ps` clear → 12 V on, driver chips cool after fifteen seconds →
agent → ROS 2 node → `ros2 node list` shows both → level the tilt, reset the ESP32, confirm
all three positions read 0.

## What is not demonstrated

No imaging. There is no camera in the system, so no volume carving has been performed and
no accuracy result is claimed. These demonstrations cover the modelling, verification and
motion control only.
